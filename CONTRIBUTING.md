## Введение

CurRate-Go - это конвертер валют на Go с desktop GUI на Wails v2. Проект использует официальный XML API Центрального Банка России для получения актуальных курсов валют.

### Что можно улучшить

- 🐛 Исправление багов
- ✨ Добавление новой функциональности
- 📝 Улучшение документации
- 🧪 Улучшение тестового покрытия
- 🎨 Улучшение UI/UX
- ⚡ Оптимизация производительности

## Настройка окружения

### Требования

- **Go 1.26** - [Скачать](https://go.dev/dl/)
- **Git 2.30+** - [Скачать](https://git-scm.com/)
- **Windows 10 (22H2+) / Windows 11** - для тестирования GUI
- **(Опционально) Wails CLI** - для разработки GUI - [Установка](https://wails.io/docs/gettingstarted/installation)

### Установка

1. **Клонировать репозиторий:**
   ```bash
   git clone https://github.com/bivlked/CurRate-Go.git
   cd CurRate-Go
   ```

2. **Установить зависимости:**
   ```bash
   go mod download
   ```

3. **Проверить установку:**
   ```bash
   go version
   # Ожидается: go version go1.26
   
   go test ./...
   # Все тесты должны пройти успешно
   ```

4. **(Опционально) Установить Wails CLI:**
   ```bash
   go install github.com/wailsapp/wails/v2/cmd/wails@latest
   ```

## Стандарты кода

### Go

- **Форматирование:** Используйте `go fmt` перед коммитом
- **Линтинг:** Код должен проходить `golangci-lint` без ошибок
- **Именование:** Следуйте [Go naming conventions](https://go.dev/doc/effective_go#names)
- **Комментарии:** Doc-комментарии на русском языке (проектное соглашение)
- **Документация:** Экспортируемые функции должны иметь doc comments

**Пример:**
```go
// Convert конвертирует сумму в указанной валюте в рубли на заданную дату.
// amount - сумма для конвертации (> 0)
// currency - валюта (USD, EUR)
// date - дата курса
func Convert(amount float64, currency models.Currency, date time.Time) (*models.ConversionResult, error) {
    // ...
}
```

### JavaScript (Frontend)

- **Vanilla JS:** Не используем фреймворки (React, Vue и т.д.)
- **Стиль:** Следуйте существующему стилю кода
- **Комментарии:** Комментарии на русском языке (для UI логики)
- **Форматирование:** Используйте единообразное форматирование

**Пример:**
```javascript
/**
 * Обновляет live preview курса валюты
 * @param {string} currency - Код валюты (USD, EUR)
 * @param {string} date - Дата в формате DD.MM.YYYY
 */
async function updateRatePreview(currency, date) {
    // ...
}
```

## Процесс создания Pull Request

### Шаг 1: Создать ветку

```bash
git checkout -b feature/your-feature-name
# или
git checkout -b fix/your-bug-fix
```

**Соглашения по именованию веток:**
- `feature/` - новая функциональность
- `fix/` - исправление бага
- `docs/` - изменения в документации
- `refactor/` - рефакторинг кода
- `test/` - добавление/изменение тестов

### Шаг 2: Внести изменения

- Внесите необходимые изменения в код
- Следуйте стандартам кода (см. выше)
- Обновите документацию, если нужно

### Шаг 3: Запустить тесты

```bash
# Запустить все тесты
go test ./...

# Запустить тесты с покрытием
go test -coverprofile=coverage.out ./...
go tool cover -html=coverage.out
```

**Требование:** Покрытие тестами должно быть >= 95% для новых изменений.

### Шаг 4: Проверить линтером

```bash
# Если golangci-lint установлен локально
golangci-lint run
```

**Примечание:** Линтер также запускается автоматически в CI/CD при создании PR. Проект использует golangci-lint v2 (`version: "2"` в `.golangci.yml`).

### Шаг 5: Обновить документацию

- Обновите `CHANGELOG.md`, если изменения значимые
- Обновите соответствующую документацию в `docs/`
- Проверьте, что все ссылки работают

### Шаг 6: Создать Pull Request

1. Закоммитьте изменения (см. [Требования к коммитам](#требования-к-коммитам))
2. Отправьте ветку на GitHub:
   ```bash
   git push origin feature/your-feature-name
   ```
3. Создайте Pull Request на GitHub
4. Заполните шаблон PR (если есть)

### Чеклист перед PR:

- [ ] Код отформатирован (`go fmt`)
- [ ] Тесты проходят (`go test ./...`)
- [ ] Покрытие тестами >= 95% для новых изменений
- [ ] Линтер не находит ошибок
- [ ] Документация обновлена
- [ ] Коммиты следуют [conventional commits](#требования-к-коммитам)
- [ ] CHANGELOG.md обновлен (если нужно)

## Требования к коммитам

Используем [Conventional Commits](https://www.conventionalcommits.org/) для единообразия и автоматизации.

### Формат коммита

```
<type>(<scope>): <description>

[optional body]

[optional footer]
```

### Типы коммитов

- `feat:` - новая функциональность
- `fix:` - исправление бага
- `docs:` - изменения в документации
- `test:` - добавление/изменение тестов
- `refactor:` - рефакторинг кода (без изменения функциональности)
- `chore:` - обновление зависимостей, конфигурации, задач сборки
- `style:` - форматирование кода (не влияет на функциональность)
- `perf:` - улучшение производительности

### Scope (опционально)

Указывает область изменений:
- `gui` - изменения в GUI
- `parser` - изменения в парсере
- `converter` - изменения в конвертере
- `cache` - изменения в кэше
- `docs` - изменения в документации

### Примеры

```bash
feat(gui): добавить live preview курса валюты
fix(parser): исправить обработку windows-1251 в XML
docs: обновить README с актуальной информацией
test(converter): добавить тесты для edge cases
refactor(cache): оптимизировать LRU кэш
chore: обновить зависимости Go
```

## Процесс ревью кода

### Для автора PR

- Будьте готовы к обсуждению и изменениям
- Отвечайте на комментарии ревьюера
- Вносите исправления в том же PR (не создавайте новый)
- Обновляйте PR, когда вносите изменения

### Для ревьюера

- Проверяйте код на корректность и соответствие стандартам
- Проверяйте, что тесты покрывают изменения
- Проверяйте, что документация обновлена
- Будьте конструктивны и вежливы в комментариях

### Критерии одобрения

- ✅ Код соответствует стандартам проекта
- ✅ Тесты проходят и покрытие >= 95%
- ✅ Линтер не находит ошибок
- ✅ Документация обновлена
- ✅ Коммиты следуют conventional commits
- ✅ Нет конфликтов с основной веткой

После одобрения PR может быть смержен.

## Тестирование

### Запуск тестов

```bash
# Все тесты
go test ./...

# Тесты с подробным выводом
go test -v ./...

# Тесты с покрытием
go test -coverprofile=coverage.out ./...
go tool cover -html=coverage.out

# Тесты frontend (Node.js 18+)
node --test tests/frontend/utils.test.js
```

### Требования к тестам

- **Покрытие:** >= 95% для новых изменений
- **Стиль:** Table-driven tests для множественных случаев
- **Именование:** `Test<FunctionName>_<Scenario>`
- **Изоляция:** Тесты должны быть независимыми

**Пример:**
```go
func TestConvert_Success(t *testing.T) {
    // ...
}

func TestConvert_InvalidCurrency(t *testing.T) {
    // ...
}
```

### Интеграционные тесты

Для тестов, требующих реального API, используйте build tag:

```go
//go:build integration

func TestFetchRates_RealAPI(t *testing.T) {
    // ...
}
```

Запуск:
```bash
go test -tags=integration ./...
```

## Обновление документации

### Когда обновлять

- При добавлении новой функциональности
- При изменении API
- При изменении процесса разработки
- При исправлении ошибок в документации

### Что обновлять

- **README.md** - если изменения значимые
- **CHANGELOG.md** - для всех значимых изменений
- **docs/** - соответствующая документация
- **Комментарии в коде** - для экспортируемых функций

### Стандарты документации

- Язык: русский (для пользовательской документации)
- Комментарии в коде: русский (проектное соглашение)
- Форматирование: Markdown
- Примеры: актуальные и проверенные

## Локальное тестирование GitHub Actions workflows

Для локального тестирования GitHub Actions workflows можно использовать инструмент [act](https://github.com/nektos/act).

### Установка act

**Вариант 1: Через Go (рекомендуется)**
```bash
go install github.com/nektos/act@latest
```

**Вариант 2: Прямой download**
Скачайте последнюю версию с [GitHub Releases](https://github.com/nektos/act/releases) и добавьте в PATH.

**Требования:**
- Docker Desktop (для Windows) или Docker Engine
- Git

### Использование

**Список всех workflows:**
```bash
act -l
```

**Тестирование конкретного workflow:**
```bash
# Тестирование lint workflow
act -W .github/workflows/lint.yml push

# Тестирование test workflow (частично, так как использует windows-latest)
act -W .github/workflows/test.yml push
```

**Тестирование с конкретным event:**
```bash
act push                  # Тестирование push event
act pull_request          # Тестирование PR event
```

### Ограничения

⚠️ **Важно:** `act` работает в Linux контейнерах, поэтому:

1. **Windows workflows не будут работать полностью:**
   - `build.yml` использует `windows-latest` - не будет работать в act
   - `test.yml` использует `windows-latest` - не будет работать в act
   - `release.yml` использует `windows-latest` - не будет работать в act

2. **Linux workflows работают частично:**
   - `lint.yml` использует `ubuntu-latest` - **будет работать** в act
   - Но некоторые GitHub Actions могут работать по-другому локально

3. **Рекомендации:**
   - Используйте `act` для проверки синтаксиса и базовой логики workflows
   - Для полного тестирования Windows workflows используйте GitHub Actions на GitHub
   - Для проверки YAML синтаксиса используйте `yamllint` (см. раздел выше)

### Примеры

**Проверка lint workflow:**
```bash
# Список jobs в lint workflow
act -l -W .github/workflows/lint.yml

# Запуск lint workflow
act -W .github/workflows/lint.yml push
```

**Проверка всех workflows (только Linux-совместимые):**
```bash
# Только lint.yml будет работать полностью
act -W .github/workflows/lint.yml push
```
